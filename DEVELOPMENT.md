## Guided Story Setup and learning

**Implemented:** New projects created through the normal project form open a full-width, central Story Setup flow instead of the screenplay editor. Project details are collected first, then the writer moves through one question at a time across protagonist, opposition, conflict, supporting characters, setting, and story direction. Every response, skip, and intentional undecided choice is stored with the project in SQLite; leaving and reopening a project resumes at the first unanswered question. Answers are mirrored into the Story Bible with writer-confirmed or intentionally-undecided provenance and decision history. Skips are retained as setup progress but do not become story facts. The review groups all questions, exposes an edit action for each, and permits proceeding when key foundations remain open. Completed setup can be reopened from the Story Bible.

Existing projects and sample projects default to setup complete and are not forced through onboarding. Setup status and responses are stored on the project; the `c2712c048f9a` Alembic migration adds the setup columns and a local application preference row for tutorial state. Tutorial state is persisted via `/api/preferences/tutorials`.

The first editor visit offers a dismissible welcome and a lightweight, keyboard-navigable tour that highlights real project, outline, editor, formatting, Story Bible, assistant, and scene-note controls. First-time Story Bible, assistant, and scene-management use also shows a dismissible contextual tip, with its dismissal persisted. The Learn button replays the full tour or focused editor, Story Bible, assistant, and scene-management guides. No paid dependency or external service is used.

The guided setup questionnaire and foundation follow-up selection are deterministic, one-question-at-a-time workflows and remain usable without Ollama. Follow-up priority uses unresolved analysis elements, setup answers, Story Bible facts, and question history; question wording comes from the local question library. Setup answers and skips are included as prior decisions so already-covered narrative areas are not re-asked. This question selection is rule-based and does not claim semantic understanding.

## Structured Story Bible and continuity review

**Implemented:** Story Bible now has project-scoped character, relationship, conflict, location, and story-event records, while existing generic StoryFact rows remain intact and continue to use their own revision history. Structured records carry source type, confirmation status, evidence, source text, source references, timestamps, and entity revision snapshots. The `/api/projects/{id}/story-bible/entities/{kind}` API supports list/create/update/delete; character merging combines aliases and links and records a merge revision. Writer-created entities default to confirmed, and records can be explicitly marked undecided or unconfirmed. The Story Bible panel exposes sections for each entity class, basic inspection/editing/deletion, and manual entry. Character fields and event dependency metadata remain available through the API even where the compact panel does not expose every field.

Scenes now store optional integer story-timeline positions and a context label (present, flashback, dream, alternate, unreliable, or unspecified). The editor exposes these in Scene notes. Continuity checks are local deterministic rules and run only on explicit request; they do not call Ollama or rewrite screenplay text. Current rules flag a confirmed death followed by a matching character cue in a later completed present-timeline scene, character cues in two confirmed locations at the same explicit position, and confirmed dependent events whose prerequisite position is not earlier. Findings include source evidence and references, can be marked intentional/explained/dismissed/needs correction, and are retained by source fingerprint. Dismissed/explained/intentional findings remain resolved on repeat analysis; changed source evidence produces a distinct finding.

**Limits:** scene cue matching is exact-name/alias matching, locations require a recognized heading and confirmed location, and overlap requires exactly equal manually assigned timeline positions. Scene ordering, vague dates, relationship changes, age, objects, and semantic exceptions are not analyzed. The interface's simple forms do not yet expose every structured field; the API supports the full schemas. A finding is a review prompt, not a claim of a plot hole.

The additive `d9c4e7a1b215` migration adds the structured tables and optional scene timeline fields after `c2712c048f9a`. Existing generic facts and screenplay rows are not converted or deleted. Downgrading to `c2712c048f9a` drops the new entity/history/finding tables and both scene timeline columns, so it also discards Phase 3 data; make a database backup before any downgrade. The downgrade path was reviewed but not executed in this session.

The local default database was verified read-only at revision `c2712c048f9a` during the Phase 4 handoff. It was not migrated during validation. Starting the backend applies the additive Phase 3 and Phase 4 migrations through `b4e81d02c7a9`; the populated upgrade test ran only against a temporary database.

**Remaining limits:** The existing schema has no relationship from a conflict to a location/event or from a story event to a screenplay scene, so the interface does not invent those links. Location category is also not modeled. Revision history stores prior snapshots; the current entity row represents the latest version. The small inline selector results are text-based and no graph view is provided.

**Implemented:** Narrative processing is split into `backend/app/narrative/` services: a conservative, standard-library premise parser; evidence validation; deterministic gap prioritization; a local question library; deterministic foundation assessment; deterministic offline analysis; and an AI-provider protocol. The parser records exact premise spans, regex extraction method, and unconfirmed provenance for detected character names/roles, organizations, objects, actions/events, time references, relationships, locations, and explicit goal phrases. Offline analysis maps only directly supported phrases into narrative elements. A named character is not automatically called the protagonist; a goal does not establish motivation; a disappearance does not establish its cause or outcome. The foundation assessment reports established, partially established, undecided, intentionally deferred, and not-applicable elements without a quality score.

When available, Ollama proposes a structured interpretation. Pydantic validation and premise-evidence checks run before saving. Unsupported explicit claims and unanchored inferences are conservatively demoted to undecided. Python ranks unresolved gaps (critical, important, optional), and the deterministic local question library phrases the next question; the model does not select or write questions. Only one question is pending at a time.

If Ollama is unavailable or times out, the API preserves the premise, returns literal extraction plus rule-based fields only where evidence supports them, and continues deterministic question selection. Unrecognized fields remain undecided. The UI labels offline analysis as rule-based and not semantic AI, displays the provider error/notice, and keeps screenplay editing available. Invalid structured JSON from an enabled model is still reported as an error rather than converted to a successful AI analysis. These safeguards do not establish semantic accuracy for an available model.

Analysis, exact extraction spans, provider mode, and the premise snapshot persist in SQLite. Questions keep their premise snapshot; a premise edit archives pending questions instead of deleting the conversation. Writer-confirmed and intentionally undecided values are preserved during reanalysis, and the Story Bible records original values, current provenance/evidence, and create/update/delete revisions. Inferred entries remain unconfirmed until the writer confirms them.

**Migrations:** `f163b8cf214e` adds premise snapshots to questions, stored literal extractions and provider notices, Story Bible provenance fields, and the `story_fact_revisions` history table. Alembic runs to head when the backend starts.

**Ollama reliability:** Ollama calls use separate configurable connect (10 seconds), read/inference (1,800 seconds), and write (60 seconds) timeouts. The API checks `/api/ps` to distinguish an already-loaded model from a model that still needs to load. Connect failures, no-first-response/model-load delays, inference timeouts (including stalls before the first token when the model was already loaded), missing models, and invalid structured output produce distinct messages. Premise analysis consumes Ollama's NDJSON stream internally; the writing assistant streams generated text to the UI. Deterministic question selection and answer saving do not call Ollama. The UI shows connection/model-loading progress, keeps screenplay editing available, preserves prompts after errors, and offers retry. Premise analysis verifies that the saved premise did not change during slow inference before saving. Inference defaults stay CPU-first (`OLLAMA_NUM_GPU=0`) with a 6,144-token context; this was raised from 4,096 after a live token count showed the earlier context was exhausted. `OLLAMA_NUM_PREDICT` controls the structured-analysis output cap (default 4,096); assistant responses have smaller caps. Truncation errors distinguish context-window exhaustion from the configured output cap. The installed model has still hit the output cap before returning a full analysis; increasing context/output further produced a request that continued beyond 30 minutes, so larger defaults are not enabled on this hardware.

**Thinking-mode check:** The installed Ollama 0.32.14 model metadata reports thinking capability. A direct probe found that `think: false` produced an empty assistant content field for `qwen3-vl:4b`; `think: "low"` returned usable content. Sorkins defaults to configurable `OLLAMA_THINK_MODE=low` rather than the unusable false mode. This reduces the configured thinking level but does not guarantee faster semantic analysis.

## Known limitations

Fountain import is intentionally lightweight: it currently places the imported text into one review scene and does not reliably recover every Fountain convention or screenplay element. Existing script content is not overwritten. Printing uses browser print-to-PDF and does not yet implement true screenplay pagination. AI-generated output is prompt-constrained but local model compliance is not yet validated; writers must review suggestions.

The premise parser uses conservative built-in patterns rather than a downloaded NLP model. It will miss arbitrary names and many complex grammatical forms; extraction is an aid, not a complete entity recognizer. The deterministic offline path intentionally leaves narrative interpretations undecided. The benchmarked local models were not reliable enough to recommend, so semantic quality remains unverified when a model is enabled.

## Architecture and local startup

The frontend is a React 19 and TypeScript single-page app served by Vite. It calls a local FastAPI backend (`backend/app`) for project, screenplay, Story Bible, narrative, setup, tutorial-preference, and Ollama operations. SQLAlchemy models persist data in SQLite; Alembic migrations live in `backend/migrations/versions`. By default, the database is `backend/data/sorkins.db`. Set `SORKINS_DATA_DIR` or `SORKINS_DATABASE_URL` in the backend process to use another location. Tests configure an isolated temporary database.

On Windows, open PowerShell in the project directory. Install dependencies once with `npm install` and `python -m pip install -r backend\requirements.txt`. Start each process in its own terminal:

1. Backend: `.\backend\run.ps1` (serves `http://127.0.0.1:8000`).
2. Frontend: `npm run dev` (open the Vite URL, normally `http://localhost:5173`).
3. Optional local AI: start Ollama separately with `ollama serve`. Configure the backend using `backend/.env.example` values in its process environment; Ollama uses `http://127.0.0.1:11434` and `qwen3-vl:4b` by default. Install the configured model separately if needed, for example `ollama pull qwen3-vl:4b`. The app does not download models. Story Setup, deterministic offline narrative behavior, and screenplay editing work without Ollama.

The backend runs `alembic upgrade head` during application import/startup, using the configured database URL. The latest migration is `b4e81d02c7a9` (`d9c4e7a1b215` is its parent; `c2712c048f9a` is earlier). To inspect the current revision manually from the project directory, run `alembic -c backend/alembic.ini current`; to apply migrations manually, run `alembic -c backend/alembic.ini upgrade head`. Keep a backup of the SQLite database before manual migration or downgrade operations. Downgrading to `c2712c048f9a` discards Phase 3 structured data and Phase 4 conflict statuses.
